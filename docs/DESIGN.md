# 设计与规则：怎样判断一句话真的更好懂？

本文件是 **36 个规则的唯一完整索引**。规则用于发现候选问题，不能靠「命中一个词」自动判定必须修改。实际执行以 [SKILL.md](../SKILL.md) 的保真和授权约束为准。

- 想开始使用：看 [README](../README.md)；
- 想验证效果：看 [评估方法](EVALUATION.md)；
- 想了解架构与路线：看 [项目方案](PROJECT_SPEC.md)。

**判断标准：** 指定目标读者后，能否指出「原文在哪里、读者可能错在哪里、为什么新写法更准确易懂、是否引入新信息」？没有具体答案，就不应强行改写。

## 一、先保真，再处理理解障碍

### 理解障碍的六个层面

从局部到整体逐级检查：

1. **识字与用词：** 这个词读者认识吗？它在当前上下文中的意思清楚吗？
2. **句法：** 读者是否能一次读出主体、动作、对象及条件？
3. **指代：** “这”“其”“该机制”“上述方案”到底指什么？
4. **概念：** 是否默认读者知道尚未介绍的术语、机制、指标？
5. **论证：** 结论与论据是否贴合？事实、推测、建议有没有混淆？
6. **阅读路径：** 为什么现在讲这个？上段留下的疑问是否被下一段回答？

低层问题优先在局部修复，高层问题需要段落或文档级处理。不要用“换几个简单词”修复整体论证断层。

### 修改优先级

**P0 绝对约束**

- 不引入新事实或原文未给出的具体因果。
- 不改变独立事实和命题的真值条件。
- 不改变否定、范围、时间、对象、归因、比较对象、完成状态和确定性。
- 不触碰受保护内容和用户未授权的编辑范围。

**P1 关键可理解性**

- 消除会导致错误理解的歧义。
- 修复句法难以解析、指代不明、前提遗漏或阅读顺序明显错乱。

**P2 表达自然性与文体**

- 更顺畅的措辞、适当分段、减少非必要术语。

**P3 篇幅和审美**

- 尽可能简洁，但不得覆盖 P0–P2。

冲突时：**宁可保留较难的专业原文并说明风险，也不能把它改成错误但好懂的句子。**

### 什么解释可以加，什么不能加？

只允许三类补充：

- **语义展开：** 将原文已表达的关系说明白。例如“甲乙存在依赖”→“甲需要乙才能完成”；前提是原文中确有这样的依赖含义。
- **指代显化：** 用可唯一确定的原有实体替换“它”“其”等代词。
- **结构提示：** “这意味着”“不过，这个结论只适用于……”之类不增加实质性新主张的衔接。

禁止两类补充：

- **事实补充：** 原文没有提到“客流数据”，就不能为了举例说系统使用客流数据。
- **因果补充：** 原文只有“相关”，就不能擅自补写“因为……所以……”。

信息确实缺少时，在 `review` 或 `annotated` 模式中标注 `【需要作者提供：……】`；默认 `clean` 模式不把标注混入正文，也不凭空补全。

## 二、36 个检查点：六类，每类六条

> **规则是审阅线索，不是机械触发器。** 任何规则都必须先判断是否真的妨碍当前目标读者理解。命中某种句式不等于必须修改。

### A. 句法与工作记忆（A01–A06）

| ID | 问题 | 处理方式 | 不应误改的情况 |
|---|---|---|---|
| A01 | 多层“的”长定语 | 把核心对象提前，修饰条件拆成独立句 | 法律/学术中必要且清楚的限定 |
| A02 | 主谓宾相隔太远 | 让核心动作尽早出现，随后补充条件 | 提前条件有助于安全操作 |
| A03 | 从句或括号套从句 | 降低嵌套层数，按事件顺序拆开 | 数学表达和精确定义 |
| A04 | 名词化/抽象动作过密 | 在施事者已知时恢复“谁做什么” | 研究术语、正式名词不能替换 |
| A05 | 语义角色关系模糊 | 明确主体、动作、对象与受影响方 | 原文未知主体不能编造 |
| A06 | 省略条件造成歧义 | 展开原文已有的否定、例外和适用范围 | 不向原文增加不存在的前提 |

**A01 例子**

- 前：`用户提交的经管理员审核通过后才可下载的报表会在次日失效。`
- 后：`用户提交报表后，需要管理员审核通过才能下载。报表会在次日失效。`
- **保真警告：** “次日”从哪一天起算不明确，改写不能擅自解释为“审核通过次日”。必要时在审阅模式提醒作者明确。

### B. 词语、术语与指代（B01–B06）

| ID | 问题 | 处理方式 | 不应误改的情况 |
|---|---|---|---|
| B01 | 生造或不常见的组合词 | 换成常见搭配，必要时拆开 | 专业领域正式名称 |
| B02 | 多个抽象名词连续堆叠 | 还原修饰关系和实际动作 | 标准化行业术语 |
| B03 | 陌生术语未经介绍 | 首次出现时使用上下文可支撑的简短解释 | 专家读者的公认常用术语 |
| B04 | 代词和“该机制”指向模糊 | 替换为确定的指代对象 | 无法唯一确定时提出疑问 |
| B05 | 同一概念换多个称呼 | 优先沿用原文主称谓 | 有明确区分的不同实体 |
| B06 | 不自然的主语-动作搭配 | 说明真实动作关系，消除误会 | 有助理解且不歧义的拟人修辞 |

**B04 例子**

- 前：`系统将报表发送给管理员，并通知用户。它可以撤回。`
- 审阅：`“它”指系统、报表还是通知？原文无法确定，不宜直接替换。`
- 禁止：自作主张改成“管理员可以撤回报表”。

### C. 信息密度与知识门槛（C01–C06）

| ID | 问题 | 处理方式 | 不应误改的情况 |
|---|---|---|---|
| C01 | 同一句堆放多项独立信息 | 将观点、依据、条件分开 | 简短并列动作本来就清楚 |
| C02 | 先给术语、后给问题 | 在授权范围内先交代用途或读者关切 | 必须先定义才能陈述的逻辑 |
| C03 | 缺少承上启下的关系 | 用不新增事实的连接句说明转折或递进 | 事实并不构成因果时不得填补 |
| C04 | 解释前预设陌生前提 | 根据已有内容补定义；缺资料则标注 | 不臆造术语定义或机制 |
| C05 | 信息量分布不均 | 让复杂概念分多步出现 | 不机械追求等长段落 |
| C06 | 多余重复与必要重复混淆 | 删除无信息重复，保留有助操作和安全的提醒 | 安全步骤、约束条件、长文关键回顾 |

**C03 例子**

- 前：`方案缩短了处理时间。成本仍未下降。`
- 后：`方案缩短了处理时间，但成本仍未下降。`
- 说明：仅明确原文已有的转折，不推断成本为什么没有下降。

### D. 文档结构与阅读路径（D01–D06）

| ID | 问题 | 处理方式 | 不应误改的情况 |
|---|---|---|---|
| D01 | 开头不回答读者关注点 | 先说明文章解决的问题及核心结论 | 学术论证、叙事文学需尊重结构 |
| D02 | 小节顺序违反依赖关系 | 先定义前提，再提出依赖该前提的结论 | 用户锁定顺序时只建议，不移动 |
| D03 | 段落只有结论、无依据 | 标明证据缺口；已有依据可前移 | 不能补编数据或引用 |
| D04 | 标题抽象或与正文不符 | 用具体读者问题或事实概括标题 | 标题、锚点、TOC 未授权时保留 |
| D05 | 转场突兀、话题跳跃 | 补清楚现有关系；无关系则建议重排 | 不虚构“因此”“由此可见” |
| D06 | 信息重复、冲突、前后不一致 | 明确标出冲突，保留原文待核实 | 不自行决定哪个版本正确 |

**D02 例子**

- 前：`先讲“缓存失效”，后介绍“什么是缓存”。`
- 后：面向初学者时，先解释缓存，再讲失效问题；面向专家时不必调序。
- 说明：**深度改序仅在获得结构编辑权限时执行。**

### E. 专业精度与文体（E01–E06）

| ID | 场景 | 推荐处理 | 不应误改的情况 |
|---|---|---|---|
| E01 | 协议、接口响应 | 解释动作可以更清楚；保留 HTTP 状态码、协议名称、响应头 | 将 `429` 换成 `500`，或把建议写成必做 |
| E02 | 代码、命令、URL 与配置 | 自然语言与机器可执行内容分开；保护参数和符号 | 改写 `GET /v1/items?limit=10` 等精确文本 |
| E03 | 科研结论 | 保留「可能」「相关」「样本」「假设」和研究限制 | 把相关性改成因果或删除局限性 |
| E04 | 医疗与安全说明 | 保留症状条件、风险和就医建议；缺证据则不加治疗方案 | 擅自添加剂量、诊断或「一定安全」 |
| E05 | 法律、合同与金融 | 保留责任方、起算日、期限单位、金额、适用范围及风险 | 把工作日改成自然日，或添加回报保证 |
| E06 | 文学、品牌与创作风格 | 只修复阻碍目标读者理解的问题；保留有意的意象与节奏 | 机械把所有隐喻翻译成白话 |

### F. 改写边界与防误改（F01–F06）

| ID | 场景 | 推荐处理 | 不应误改的情况 |
|---|---|---|---|
| F01 | 原意存在真实歧义 | 保留歧义并请作者确认；不代替作者决定 | 猜测人物或代词指向 |
| F02 | 原文已经清楚 | 原样保留；零改动是有效结果 | 为追求改动数量随意换词 |
| F03 | 时间、状态与确定程度 | 逐一核对「计划」「测试中」「尚未通过」「已完成」 | 把未来时写成已完成，或把「尚未通过」解释为测试失败 |
| F04 | 结构化或可执行内容 | 保留 JSON、YAML、命令、代码和数据的精确字面形式 | 把 `false` 改成 `true`，或重写命令参数 |
| F05 | 原文缺少必要资料 | 报告具体缺口；只改写已有的部分 | 编造缺失的成本、来源、机制或证据 |
| F06 | 许可、适用范围与承诺 | 保留「仅」「不得」「至少」「受邀」「试用」等关键限定 | 把部分用户可用改写成所有人可用 |

**六类和 36 条规则按 ID 与 [36 条合成案例](../tests/fixtures.json) 一一对应。** 这只是检查与演示对照，并不意味着每条都经过真人理解实验验证。

## 三、执行流程：从读者疑问到保真复核

### Step 1 — 确认任务边界

解析用户的目标、读者、文体、模式、编辑范围和受保护内容。未指定时使用 `standard + context-aware audience + clean output`。只读请求绝不写文件。

### Step 2 — 锁定原文事实与语义

在内部建立「命题清单」（proposition ledger），每项至少辨认：

- 主体 / 动作 / 对象
- 数字 / 单位 / 时间 / 比较对象
- 否定 / 条件 / 限定 / 例外
- 可能性、事实、推测、意见、建议、计划、已完成状态
- 归因、引文与信息出处

**示例：** `预计年底前完成，尚未通过测试。` → 只能保留「预计年底前完成」和「尚未通过测试」。**「尚未通过」不能替换成「测试失败」或「尚未开始测试」**；原文没有足够信息区分这些情况。

### Step 3 — 找到真正的理解障碍

按 A–F 分类标注问题，并判断：

- `severity`: `critical`（可能误解原意）/ `major`（明显阅读阻碍）/ `minor`（轻微不自然）
- `level`: `term` / `sentence` / `paragraph` / `document`
- `evidence`: 指向**原文具体位置或文本**，不可只给泛泛的“难懂”评价
- `fix`: 优先选择最小有效改动

不要求每篇文章都命中每条规则；不要为了填满检查表而构造问题。

### Step 4 — 按读者理解顺序改写

按以下顺序尝试：

1. 保留已经清楚的句子。
2. 解除歧义、长定语、嵌套和不自然搭配。
3. 保持概念首次出现前后的解释位置合理。
4. 对段落做局部衔接；`deep` 模式在取得结构编辑授权后，才允许全文重排。
5. 必要时拆句、增补标点或原文已蕴含的关系，长度可升可降。

### Step 5 — 双向保真检查

不仅检查“改写有无凭空增加”，还要检查“原文有无被删减或弱化”。

- **Original → Revised：** 每个独立命题能否在新稿找到对应？
- **Revised → Original：** 新稿每个事实性主张是否都可追溯到原文或用户提供资料？
- 检查数字、否定、条件、时间、主体、归因、术语、代码、链接、标题锚点、列表项。
- 如存在无法消解的歧义，撤销该局部改写并报告问题（若输出模式允许）。

### Step 6 — 交付

- `clean`: 只输出最终稿；没有可改之处则照原文输出。
- `review`: 输出按影响排序的问题、原文片段、原因、改法与边界；不编辑文件。
- `annotated`: 改写稿 + 简短关键变更说明 + 仍待作者确认的问题。
- `diff`: 原文与改写对照，便于审阅；不要声称机器计算的精确 diff（除非实际运行了 diff 工具）。
- `diagnosis`: 专门用于定位问题，包含判断依据和待验证事项；不默认给出整篇新稿。

## 四、文件与高风险文本的保护

### 默认保护的内容

除非用户明确授权且能验证准确：

- 数字、百分比、币种、单位、日期、时间、版本号
- 人名、组织名、产品名、地名和专业术语
- “可能”“通常”“仅”“至少”“不超过”“计划”“据报道”等限定
- 否定、例外、适用范围、比较基准、归因和引文内容
- 代码块、行内代码、SQL、JSON、YAML、shell 命令、正则表达式、公式
- URL、Markdown 链接目标、图片路径、锚点、文件路径、接口路径、环境变量
- 表格中的数据和列含义
- 用户指定的原文段落、法律条款、合规声明、学术引文

### Markdown 文件如何安全编辑

- 仅修改用户授权的自然语言正文；代码块与 frontmatter 默认只读。
- 默认不改标题文字、层级与顺序，避免自动锚点、目录和站内链接失效。
- `deep` 模式授权标题/结构变更时，应同步检查目录、锚点、内部链接、脚注引用与列表编号。
- 保留每项独立事实；列表即使很长也不能为了精简而删除条目。
- 对不一致的数据**报警而非猜一个正确值**。
- 保留示例所表示的实际机制；不为了口语化破坏操作精度。

### 高风险文本的特殊处理

- 医疗：区分症状、诊断、可能性和建议；不增加治疗方案。
- 金融：不新增收益预测、风险水平或投资建议。
- 法律：不改责任主体、例外、义务程度、期限和条件。
- 科研：不强化结论，不增加统计显著性或因果性，不删局限性。
- 安全操作：保留必要重复提醒，不能删除可能影响安全的步骤。
