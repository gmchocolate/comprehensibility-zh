# Comprehensibility-zh 项目方案

> **定位：** 一个让中文内容更容易被目标读者准确理解的 Agent Skill。  
> **现状：** 已有可供 Agent 读取的规则文档、36 条合成案例和静态测试；尚无跨客户端完整兼容性验证或中文真人理解实验。  
> **文档职责：** 本文件说明项目边界、交付结构、协作规范和路线图，不重复贴一遍规则全文。

## 一、为什么要做？

不少文字不是事实错误，而是**阅读顺序不合适**：主要动作藏在长定语后面，多个条件挤成一句话，重要术语没有解释，段落跳得太快。读者花力气理解句子结构，却没有真正理解内容。

本项目不把「去 AI 味」「更短」「更有营销感」作为结果指标。优先解决三个问题：

1. **读者会不会理解错？** 例如谁做了什么，条件何时成立，数据支持哪个结论。
2. **读者是否需要来回读？** 例如长距离依赖、名词堆叠、解释太晚出现。
3. **读者能否顺着文章走下去？** 每一节是否回答自然出现的下一个疑问。

当「表达自然」和「事实准确」冲突时，必须选准确。原文缺失信息时，编辑只能标明缺口，不能自造事实。研究依据及其局限见 [RESEARCH.md](RESEARCH.md)。

## 二、给谁用？

| 读者和场景 | 最容易遇到的问题 | 推荐做法 |
|---|---|---|
| 第一次了解产品的客户 | 功能说明全是抽象词 | 先讲实际用途，再讲能力和范围 |
| 新加入项目的工程师 | 前提未说明，术语和接口混杂 | 在需要操作之前解释依赖，保留接口原样 |
| 阅读业务分析的管理者 | 观点、数据、推断混在一起 | 分开结论、证据、限制和下一步 |
| 面向普通人的科普作者 | 一个句子装进太多新概念 | 先解释必要概念，再展示它们的关系 |
| 学术与专业写作者 | 句法复杂，但术语具有精确含义 | 优先拆句，不以口语化替代专业定义 |

读者没有统一的「正确阅读顺序」。产品说明可能先回答「这能帮我做什么」，科研论文可能先说明问题与方法，操作规程必须确保前置安全条件不会被移到后面。

## 三、项目最重要的约束

从高到低：

1. **事实保真和权限：** 不虚构、不遗漏、不偷换；未经许可不写文件、不移动受保护内容。
2. **减少误读：** 保护否定、条件、主体、时间、范围、完成状态和因果边界。
3. **降低阅读负担：** 用适合读者的词汇、句法和解释顺序表达同一内容。
4. **文体和风格：** 保留必要的专业性与作者声音。
5. **篇幅和美观：** 不以字数或分段数作为目标。

### 可改与不可改的边界

**可以：** 拆解长定语、显化唯一确定的代词、把一个句子里的原有条件拆开、把原本明确的转折表达清楚、在授权范围内调整文章顺序。

**不能：** 擅加研究结论、价格、功能、数据、客户案例、风险建议；把「尚未通过测试」替换成「测试失败」；把「仅受邀企业」改成「全部用户」；更改命令、API 路径、链接目标或 JSON 内容。

**需要作者参与：** 代词没有唯一指向、原文证据不足、相邻章节数据冲突、缺少专业定义。此时应该指出问题，而不是用一句流利的假设掩盖它。

实际执行规则见 [SKILL.md](../SKILL.md)，36 条具体检查见 [DESIGN.md](DESIGN.md)。

## 四、用户怎样调用？

### 四种模式

| 模式 | 使用时机 | 修改幅度 | 文件写入 |
|---|---|---|---|
| `review` | 想先知道哪里难读 | 仅诊断 | 禁止 |
| `light` | 原稿大体清楚 | 只改有问题的词句 | 需用户另行授权 |
| `standard`（默认） | 需要一版更好读的稿子 | 句段级 | 需用户另行授权 |
| `deep` | 全文顺序不适合读者 | 可以提出或实施结构重组 | 需要写入授权；重排还需结构授权 |

**输出方式独立于模式。** 默认输出干净正文；可选择 `review` 问题清单、`annotated` 重要改动与待确认、`diff` 前后对照、`diagnosis` 只诊断。

### 三条可复制请求

**只优化文字：**

```text
用 comprehensibility-zh 的 standard 模式优化下面的文字。
读者：第一次接触这一领域的普通人。
必须保留事实、条件、数据、完成状态和术语含义。
信息不足时不要自行补全；只输出改写稿。
```

**只审阅：**

```text
用 comprehensibility-zh 的 review 模式审阅这份技术文档。
指出准确位置、理解障碍、可能误解和建议；不要修改文件。
```

**处理多文件：**

```text
用 comprehensibility-zh 的 deep 模式优化 README.md、SKILL.md 和 docs/。
读者：第一次使用本项目的开发者。允许修改文档标题和章节顺序。
以 SKILL.md 为执行契约，以 docs/DESIGN.md 为规则索引，
核对各文档术语、示例、编号和链接的一致性；不要改代码、协议或数据。
输出改动摘要、测试结果与未解决问题。
```

## 五、仓库里的文件各负责什么？

| 文件 | 唯一职责 | 不应承载什么 |
|---|---|---|
| [`README.md`](../README.md) | 让第一次来的读者知道用途、安装、限制和入口 | 规则全文与研究长篇 |
| [`SKILL.md`](../SKILL.md) | Agent 执行的模式、流程、权限、保真约束 | 未验证的效果宣传 |
| [`DESIGN.md`](DESIGN.md) | 36 条规则的**唯一完整索引**、适用例外和边界 | 重复的安装指南 |
| [`EVALUATION.md`](EVALUATION.md) | 静态、语义和真人理解的分层验证方案 | 把测试数量当效果指标 |
| [`RESEARCH.md`](RESEARCH.md) | 研究启发、引用、不能推出的结论 | 将英语研究直接宣称为中文效果 |
| [`examples.md`](../examples/examples.md) | 正反例和改写依据 | 混入未经说明的真实业务数据 |
| [`fixtures.json`](../tests/fixtures.json) | 36 条合成案例的输入和期望行为 | 模型输出、真人实验分数 |
| [`test_repository.py`](../tests/test_repository.py) | 校验格式、编号、链接、保护样本 | 假装做了真人理解测试 |
| `CHANGELOG.md` / `CONTRIBUTING.md` | 记录变更与贡献规则 | 模糊的产品愿景口号 |

这套组织方式避免一条规则同时在多个文件出现多个「最终版本」。**发生冲突时：以 `SKILL.md` 的安全与执行要求为准；规则定义查 `DESIGN.md`；效果证据查 `EVALUATION.md`。**

## 六、处理一篇文章的实际过程

1. **确定读者：** 先判定背景知识、文本用途以及允许的编辑范围。
2. **锁定原意：** 分别记录每项命题、数字、条件、否定、归因、时态及受保护片段。
3. **定位困难：** 从词语、句子、关系、信息密度到全文顺序检查，按误读风险排序。
4. **最小改写：** 能拆一个句子就不先重写全篇；读者已经能懂的地方不动。
5. **双向校验：** 原文每项意思是否保留？新稿每项事实有无依据？
6. **交付：** 改写稿与必要的待确认问题；对文件修改须同步验证链接、编号和测试。

一个常见错误是把「改得更具体」理解为「编出细节」。原文只说「多源数据」，就不能自行列出「客流、租金、营收预测」；这类缺口必须由作者补充。

## 七、规则与测试怎么对应？

规则分 A–F 六类、每类六条，共 **36 条**。`tests/fixtures.json` 中的 `id` 与规则编号一一对应：

- A：句法与工作记忆；B：词语、术语、指代；
- C：信息密度与知识门槛；D：篇章与阅读路径；
- E：专业精度与文体；F：编辑边界与防误改。

**注意：** 每条规则对应一个人工合成案例，只说明覆盖关系，不是模型已经通过测试；静态 CI 只验证文件格式、引用和编号。要比较模型行为，需要另外记录模型版本、具体提示、原始输出、人工保真审核和失败案例。要声明读者理解提升，必须做真正的阅读实验。详见 [EVALUATION.md](EVALUATION.md)。

## 八、路线图与质量要求

### 现有基础

- 根目录 Agent Skill 与四种调用模式。
- 36 条规则和 36 条合成案例，附有禁止误改的反例。
- 公开文档、MIT 许可证和无模型依赖的结构测试。

### 下一阶段：增强规则可靠性

- [ ] 维护可复现的模型输出样本，而不只是人工构造的输入。
- [ ] 按「新增事实、遗漏条件、状态漂移、指代猜测、结构破坏」记录失败原因。
- [ ] 增加不应修改的负例与长文跨段落案例。
- [ ] 补齐常见 Agent 客户端的真实安装和调用记录。

### 再下一阶段：验证理解效果

- [ ] 公开正式读者实验设计和样本选择。
- [ ] 先对原文与各改写版本做独立保真核查。
- [ ] 收集中文读者理解题、耗时和主观难度数据。
- [ ] 报告正向、无效和负向结果及局限性。

**不做虚假的「可理解性 0–100 分」：** 未经校准的模型自评分不能被包装为科学测量。

## 九、开源协作与版本

采用 MIT 许可证。欢迎问题案例、规则适用范围、反例、兼容性记录和评估方法贡献。外部材料要确认可公开并遵守原许可，不应直接复制其他 Skill 的大段规则或论文图表。

建议每份规则 PR 至少说明：目标读者、原文、可能误解、推荐改法、保留的事实/条件、不应这样改的反例、验证方式。贡献流程见 [CONTRIBUTING.md](../CONTRIBUTING.md)。

变更分级可参考语义化版本：破坏兼容的模式/接口调整为主版本，新增兼容能力为次版本，修正文档和案例为修订版本。**版本号记录发布意图，不等于已经做了跨模型实证。**

## 十、常见问题

**既然 Humanizer-zh 可以润色，为什么还需要这个项目？**  语句是否自然与读者是否准确理解，不是同一个问题。这里重点修复关系、信息顺序和知识门槛；它们可以互补。

**是不是句子越短越好？**  不是。拆句如果丢掉条件或因果关系，就只是变短，不是变清楚。

**没有资料，能否自动补充示例？**  不能把编造案例当作事实。可以在用户明确要求虚构教学例子时生成，并醒目标记为「虚构」。

**专业文章是不是要全部变成大白话？**  不是。对专家有用且精确的术语应该保留；需要解释时，先确认读者和可用资料。

**模型能否替自己打分？**  可以辅助发现问题，却不能把模型评分当作真人理解结果。发布效果数字前，需要真实的实验设计与数据。

**能否自动编辑 GitHub 仓库？**  取决于 Agent 的工具和用户授权。Skill 本身只是一套编辑指令，不会凭空获得读写仓库的权限。
