# Comprehensibility-zh：中文可理解性优化 Skill —— 开源仓库完整设计与实施规范

> **一句话定位：** 不以“像不像 AI 写的”为目标，而以“目标读者能否省力、准确地理解”为目标。  
> **项目形态：** 基于开放 Agent Skills 格式的跨 Agent 中文文本审阅与改写 Skill。  
> **文档版本：** 0.1.0 · 2026-11-06 · 开源发布准备稿。  
> **状态说明：** 本文是项目规范和首发实施方案，不代表已完成用户实验，也不宣称已证明能提高阅读理解分数。

---

## 0. 项目摘要

**Comprehensibility-zh** 是一个面向中文读者的「可理解性优化」Agent Skill，专门处理**内容本身可能是正确的，但读起来费劲**的问题。

它要解决的不只是 AI 套话、模板腔、冗长修辞，而是更底层的阅读障碍：长定语、多层嵌套、远距离依赖、施事关系模糊、陌生概念未解释、信息过度压缩、段落之间跳跃，以及文章没有按照读者的问题展开。

它的核心承诺是：

1. **先保真，再变好懂。** 不改变事实、立场、条件、范围、因果、确定程度、数字和归因。
2. **减少理解成本，而不是追求最短。** 必要时可拆句、增补连接词、展开隐含关系；但不虚构背景、证据、机制或案例。
3. **同时优化句子与文章。** 既处理一句话为什么费劲，也处理整篇文章为什么读不下去。
4. **尊重读者与文体。** 普通读者、专家、客户、学生需要不同程度的解释；学术、法律、技术、营销文本不能被粗暴地统一口语化。
5. **可审阅、可测试、可回退。** 用户可以仅审阅、最小改写或深度重构；每个实质性改动都应能说明其必要性。

适用于：产品说明、官网内容、帮助中心、技术文档、商业报告、科普、教育内容、论文通俗解读、面向非专业人员的专业沟通。

不承诺：识别 AI 写作、绕过检测器、核实外部事实、替代专业审校、保证任何特定读者读懂。

## 1. 背景与研究依据

### 1.1 为什么需要另一个 Skill

现有的 Humanizer-zh（<https://github.com/op7418/Humanizer-zh>）主要关注空话、重复、模板化表达和作者声音的保留，也包含部分中文长定语与被动句检查。本项目与其**互补而非替代**：

| 维度 | Humanizer-zh | Comprehensibility-zh |
|---|---|---|
| 核心问题 | 说得是否自然、是否空泛 | 读者是否容易正确理解 |
| 优先目标 | 自然度、表达质量与保真 | 理解负担、阅读顺序与保真 |
| 修改尺度 | 常以句段局部编辑为主 | 句子、段落、整篇结构 |
| 长度导向 | 去掉无效重复，长度并非唯一目标 | 必要时允许变长，以减少推理负担 |
| 特别关注 | 模板句、套话、冗余表达 | 认知负担、知识门槛、逻辑桥梁 |
| 输出 | 润色稿 / 审阅建议 | 改写稿 / 问题诊断 / 保真审阅 |

**项目不应复制 Humanizer-zh 的 31 条规则或原文表达。** 若选择参考或复用该仓库代码/文本，需核查其对应版本许可证并保留适用的版权声明；默认采用本项目独立编写的规则。

### 1.2 科研启发：为什么“正确”不等于“好理解”

Clark、Martin、Mahowald 于 2026-10-21 发布的论文 *Why is AI-generated language so hard to understand?*（<https://arxiv.org/html/2610.29162v1>）研究了 AI 生成英语中的六类与阅读处理成本相关的语言特征：

1. **低频词语组合**（low-frequency n-grams）：词与词组合不常见，读者难以预测后续信息。
2. **较长句法依赖距离**（dependency length）：彼此相关的词隔得很远，增加工作记忆负担。
3. **宾语关系从句**（object relative clauses）：某些嵌套结构处理起来更费力。
4. **连续名词堆叠**（stacked noun compounds）：修饰关系压缩在一串名词里，可能产生歧义。
5. **名词临时转作动词**（denominal verbs）：要求读者临时推断非常规用法。
6. **不符合常规语义选择的无生命主语**（inanimate subjects）：某些动作与主语搭配不符合通常预期。

论文还通过长度惩罚训练实验，支持「优化目标偏好更高信息密度，可能使语言偏离人类习惯」的概念验证假说。这是本项目**设计动机**，不是直接的中文产品效果证据。

**证据边界必须明确：** 论文主要研究英语、有限模型和任务；使用语言处理难度相关特征作为代理指标，没有证明本项目的中文规则有效，也没有完成本项目所需的中文读者 A/B 理解实验。英文结构不应一比一映射成中文语法规则。本项目将其作为待检验的研究启发，而非既成结论。

### 1.3 核心原则：压缩文字 ≠ 压缩读者理解成本

例子：

- 原文：`基于多源异构数据融合的选址决策优化能力，可赋能门店增长。`
- 不合格的“简化”：`融合多源数据，优化选址，赋能增长。`（仍旧抽象，而且“增长”的含义没有依据）
- 更合适的改写：`系统把不同来源的数据放在一起分析，帮助团队判断一个位置是否适合开店。`（拆开抽象的动作与目的；不额外承诺增长结果）

好的可理解性优化不是“多用短句”这么简单，而是**把隐藏在表达中的必要关系显式化**，同时不添加超出来源的信息。

## 2. 愿景、目标与非目标

### 2.1 愿景

**让准确的信息，以适合人类阅读和理解的方式被表达。**

英文短句：*Make meaning easier to grasp, without changing what is true.*

### 2.2 目标（按优先级）

1. **语义和事实保真：** 原文的独立事实、否定、条件、概率、限制、比较基准、时间、主体与归因不丢失、不新增。
2. **减少歧义：** 尤其关注“谁做了什么”“修饰哪个对象”“哪个结论由什么证据支持”。
3. **降低阅读时的工作记忆负担：** 避免读者需要同时记住过多前置条件才能读懂句尾。
4. **补足内部表达连接：** 将原文已有但被压缩的概念关系拆开说清，必要时解释行文中的代词指向。
5. **形成符合阅读顺序的结构：** 从“用户正在困惑什么”开始，逐步给出答案、理由、条件和下一步。
6. **尊重目标读者：** 该解释的解释，专家熟悉且重要的术语保留。
7. **最小充分编辑：** 清楚的文本不修改，避免写作风格被同质化。

### 2.3 不做什么

- 不把项目定位为“去 AI 味”或 AI 检测规避工具。
- 不以纯粹缩短篇幅、降低生僻字比例、增加分段数量作为成功判据。
- 不保证所有读者、所有文体都得到同等收益。
- 不虚构例子、比喻、数据、来源、使用体验、产品性能或角色经历。
- 不把相关性改为因果，不把“可能”改为“必然”，不把“计划”改为“已完成”。
- 不替代学术同行评审、法务意见、医疗决策或事实调查。
- 不擅自改动代码、配置、公式、链接、引用、表格数值和程序接口。

## 3. 使用人群、场景与模式

### 3.1 推荐用户

| 目标读者 | 典型内容 | 优化重点 |
|---|---|---|
| 普通大众 | 公告、科普、产品介绍 | 降术语门槛、明确实际含义 |
| 产品客户 | 官网、帮助中心、销售材料 | 先解决问题，再解释能力，减少抽象名词 |
| 技术团队 | API 文档、变更说明、故障报告 | 明确操作对象、前提、顺序和例外，保留代码精度 |
| 管理决策者 | 周报、分析报告、投标方案 | 先结论后依据，清楚区分事实、推断和建议 |
| 学术读者 | 论文摘要、讨论段落 | 降低句法负担，但严格保留术语和限定 |
| 学生/初学者 | 教材、知识解释 | 定义前置概念，分层讲解，标示未知点 |

### 3.2 四种调用模式

| 模式 | 用户指令示例 | 默认输出 | 可改变结构吗 |
|---|---|---|---|
| `review` 审阅 | “检查哪里难懂，不改稿” | 逐项问题 + 具体建议 | 不改文件 |
| `light` 轻量优化 | “只改难懂句子” | 最终稿 | 原则上不 |
| `standard` 标准优化（默认） | “让普通读者更容易理解” | 最终稿 | 可调整局部段落 |
| `deep` 深度重构 | “按读者的疑问重新组织全文” | 最终稿 + 可选变更摘要 | 可，但必须授权 |

默认读者：**具备普通高中或同等阅读能力、不了解行业背景的成年人**。这只是编辑操作上的起点，不是对真实读者能力的判断。若正文明确面向专业人士，则以文体及上下文识别的专业读者为准，不强行通俗化。

默认处理：`standard`；默认交付：**仅最终稿**。只有用户要求分析/比较时才展示长篇诊断。

### 3.3 用户可选约束

- `audience`: `general` / `beginner` / `professional` / `executive` / `custom`
- `mode`: `review` / `light` / `standard` / `deep`
- `genre`: `auto` / `product` / `technical` / `academic` / `legal` / `medical` / `business` / `education` / `creative`
- `edit_scope`: `sentences` / `paragraphs` / `document`
- `terminology`: `preserve`（默认）/ `explain-on-first-use` / `plain-language`
- `format`: `clean`（默认）/ `annotated` / `diff` / `diagnosis`
- `protected_terms`: 用户列出的不得改变的专有词、名词或短语
- `protected_spans`: 代码、数字、路径、引用、契约条款、用户选定的段落等
- `length_policy`: `as-needed`（默认），**不是**自动缩写或扩写

这些是**供 Agent 识别的约定字段**，v0.1 不提供实际 CLI 解析器，不应宣称实现了机器参数 API。自然语言指令同样有效。

## 4. 核心设计：理解路径优先于措辞

### 4.1 读者理解的六级模型

从局部到整体逐级检查：

1. **识字与用词：** 这个词读者认识吗？它在当前上下文中的意思清楚吗？
2. **句法：** 读者是否能一次读出主体、动作、对象及条件？
3. **指代：** “这”“其”“该机制”“上述方案”到底指什么？
4. **概念：** 是否默认读者知道尚未介绍的术语、机制、指标？
5. **论证：** 结论与论据是否贴合？事实、推测、建议有没有混淆？
6. **阅读路径：** 为什么现在讲这个？上段留下的疑问是否被下一段回答？

低层问题优先在局部修复，高层问题需要段落或文档级处理。不要用“换几个简单词”修复整体论证断层。

### 4.2 优先级冲突处理

**P0 绝对约束**

- 不引入新事实或原文未给出的具体因果。
- 不改变独立事实和命题的真值条件。
- 不改变否定、范围、时间、对象、归因、比较对象、完成状态和确定性。
- 不触碰受保护内容和用户未授权的编辑范围。

**P1 关键可理解性**

- 消除会导致错误理解的歧义。
- 修复句法难以解析、指代不明、前提遗漏或阅读顺序明显错乱。

**P2 表达自然性与文体**

- 更顺畅的措辞、适当分段、减少非必要术语。

**P3 篇幅和审美**

- 尽可能简洁，但不得覆盖 P0–P2。

冲突时：**宁可保留较难的专业原文并说明风险，也不能把它改成错误但好懂的句子。**

### 4.3 不臆造的“桥梁句”

只允许三类补充：

- **语义展开：** 将原文已表达的关系说明白。例如“甲乙存在依赖”→“甲需要乙才能完成”；前提是原文中确有这样的依赖含义。
- **指代显化：** 用可唯一确定的原有实体替换“它”“其”等代词。
- **结构提示：** “这意味着”“不过，这个结论只适用于……”之类不增加实质性新主张的衔接。

禁止两类补充：

- **事实补充：** 原文没有提到“客流数据”，就不能为了举例说系统使用客流数据。
- **因果补充：** 原文只有“相关”，就不能擅自补写“因为……所以……”。

信息确实缺少时，在 `review` 或 `annotated` 模式中标注 `【需要作者提供：……】`；默认 `clean` 模式不把标注混入正文，也不凭空补全。

## 5. 规则系统：六类 30 个检查点

> **规则是审阅线索，不是机械触发器。** 任何规则都必须先判断是否真的妨碍当前目标读者理解。命中某种句式不等于必须修改。

### A. 句法与工作记忆（A01–A06）

| ID | 问题 | 处理方式 | 不应误改的情况 |
|---|---|---|---|
| A01 | 多层“的”长定语 | 把核心对象提前，修饰条件拆成独立句 | 法律/学术中必要且清楚的限定 |
| A02 | 主谓宾相隔太远 | 让核心动作尽早出现，随后补充条件 | 提前条件有助于安全操作 |
| A03 | 从句或括号套从句 | 降低嵌套层数，按事件顺序拆开 | 数学表达和精确定义 |
| A04 | 名词化/抽象动作过密 | 在施事者已知时恢复“谁做什么” | 研究术语、正式名词不能替换 |
| A05 | 语义角色关系模糊 | 明确主体、动作、对象与受影响方 | 原文未知主体不能编造 |
| A06 | 省略条件造成歧义 | 展开原文已有的否定、例外和适用范围 | 不向原文增加不存在的前提 |

**A01 例子**

- 前：`用户提交的经管理员审核通过后才可下载的报表会在次日失效。`
- 后：`用户提交报表后，需要管理员审核通过才能下载。报表会在次日失效。`
- **保真警告：** “次日”从哪一天起算不明确，改写不能擅自解释为“审核通过次日”。必要时在审阅模式提醒作者明确。

### B. 词语、术语与指代（B01–B06）

| ID | 问题 | 处理方式 | 不应误改的情况 |
|---|---|---|---|
| B01 | 生造或不常见的组合词 | 换成常见搭配，必要时拆开 | 专业领域正式名称 |
| B02 | 多个抽象名词连续堆叠 | 还原修饰关系和实际动作 | 标准化行业术语 |
| B03 | 陌生术语未经介绍 | 首次出现时使用上下文可支撑的简短解释 | 专家读者的公认常用术语 |
| B04 | 代词和“该机制”指向模糊 | 替换为确定的指代对象 | 无法唯一确定时提出疑问 |
| B05 | 同一概念换多个称呼 | 优先沿用原文主称谓 | 有明确区分的不同实体 |
| B06 | 不自然的主语-动作搭配 | 说明真实动作关系，消除误会 | 有助理解且不歧义的拟人修辞 |

**B04 例子**

- 前：`系统将报表发送给管理员，并通知用户。它可以撤回。`
- 审阅：`“它”指系统、报表还是通知？原文无法确定，不宜直接替换。`
- 禁止：自作主张改成“管理员可以撤回报表”。

### C. 信息密度与知识门槛（C01–C06）

| ID | 问题 | 处理方式 | 不应误改的情况 |
|---|---|---|---|
| C01 | 同一句堆放多项独立信息 | 将观点、依据、条件分开 | 简短并列动作本来就清楚 |
| C02 | 先给术语、后给问题 | 在授权范围内先交代用途或读者关切 | 必须先定义才能陈述的逻辑 |
| C03 | 缺少承上启下的关系 | 用不新增事实的连接句说明转折或递进 | 事实并不构成因果时不得填补 |
| C04 | 解释前预设陌生前提 | 根据已有内容补定义；缺资料则标注 | 不臆造术语定义或机制 |
| C05 | 信息量分布不均 | 让复杂概念分多步出现 | 不机械追求等长段落 |
| C06 | 多余重复与必要重复混淆 | 删除无信息重复，保留有助操作和安全的提醒 | 安全步骤、约束条件、长文关键回顾 |

**C03 例子**

- 前：`方案缩短了处理时间。成本仍未下降。`
- 后：`方案缩短了处理时间，但成本仍未下降。`
- 说明：仅明确原文已有的转折，不推断成本为什么没有下降。

### D. 文档结构与阅读路径（D01–D06）

| ID | 问题 | 处理方式 | 不应误改的情况 |
|---|---|---|---|
| D01 | 开头不回答读者关注点 | 先说明文章解决的问题及核心结论 | 学术论证、叙事文学需尊重结构 |
| D02 | 小节顺序违反依赖关系 | 先定义前提，再提出依赖该前提的结论 | 用户锁定顺序时只建议，不移动 |
| D03 | 段落只有结论、无依据 | 标明证据缺口；已有依据可前移 | 不能补编数据或引用 |
| D04 | 标题抽象或与正文不符 | 用具体读者问题或事实概括标题 | 标题、锚点、TOC 未授权时保留 |
| D05 | 转场突兀、话题跳跃 | 补清楚现有关系；无关系则建议重排 | 不虚构“因此”“由此可见” |
| D06 | 信息重复、冲突、前后不一致 | 明确标出冲突，保留原文待核实 | 不自行决定哪个版本正确 |

**D02 例子**

- 前：`先讲“缓存失效”，后介绍“什么是缓存”。`
- 后：面向初学者时，先解释缓存，再讲失效问题；面向专家时不必调序。
- 说明：**深度改序仅在获得结构编辑权限时执行。**

### E. 文体与特殊内容（E01–E03）

| ID | 场景 | 规则 |
|---|---|---|
| E01 | 技术、代码与 API | 保留路径、函数名、参数、类型、命令、响应字段、代码语义；解释可以改，规范不能随意改 |
| E02 | 学术、法律、医学、金融 | 保留专业词、限制性表述、出处、数字单位、风险提示；不得用通俗话替代本应精确的法定/医学含义 |
| E03 | 品牌、营销、创意写作 | 可以增强理解，但不统一抹除作者风格、意象、节奏和有价值的比喻 |

### F. 编辑与交付安全（F01–F03）

| ID | 场景 | 规则 |
|---|---|---|
| F01 | 无法确定原意 | 不猜、不强行改；在诊断中提出具体歧义 |
| F02 | 已经清楚 | 保留原文；零修改是合法输出 |
| F03 | 新增解释或重排 | 在改变结构或增加非事实性的读者提示后，必须进行保真和引用一致性复查 |

## 6. 执行算法：六步可审计流程

### Step 1 — 确认任务边界

解析用户的目标、读者、文体、模式、编辑范围和受保护内容。未指定时使用 `standard + context-aware audience + clean output`。只读请求绝不写文件。

### Step 2 — 锁定原文事实与语义

在内部建立「命题清单」（proposition ledger），每项至少辨认：

- 主体 / 动作 / 对象
- 数字 / 单位 / 时间 / 比较对象
- 否定 / 条件 / 限定 / 例外
- 可能性、事实、推测、意见、建议、计划、已完成状态
- 归因、引文与信息出处

**示例：** `预计年底前完成，尚未通过测试。` → `计划完成时间：年底前`、`当前测试状态：未通过/尚未通过（按上下文保持准确原意）`。不得变为“年底前正式上线”。

### Step 3 — 找到真正的理解障碍

按 A–F 分类标注问题，并判断：

- `severity`: `critical`（可能误解原意）/ `major`（明显阅读阻碍）/ `minor`（轻微不自然）
- `level`: `term` / `sentence` / `paragraph` / `document`
- `evidence`: 指向**原文具体位置或文本**，不可只给泛泛的“难懂”评价
- `fix`: 优先选择最小有效改动

不要求每篇文章都命中每条规则；不要为了填满检查表而构造问题。

### Step 4 — 按读者理解顺序改写

按以下顺序尝试：

1. 保留已经清楚的句子。
2. 解除歧义、长定语、嵌套和不自然搭配。
3. 保持概念首次出现前后的解释位置合理。
4. 对段落做局部衔接；`deep` 模式才默认允许全文结构重排。
5. 必要时拆句、增补标点或原文已蕴含的关系，长度可升可降。

### Step 5 — 双向保真检查

不仅检查“改写有无凭空增加”，还要检查“原文有无被删减或弱化”。

- **Original → Revised：** 每个独立命题能否在新稿找到对应？
- **Revised → Original：** 新稿每个事实性主张是否都可追溯到原文或用户提供资料？
- 检查数字、否定、条件、时间、主体、归因、术语、代码、链接、标题锚点、列表项。
- 如存在无法消解的歧义，撤销该局部改写并报告问题（若输出模式允许）。

### Step 6 — 交付

- `clean`: 只输出最终稿；没有可改之处则照原文输出。
- `review`: 输出按影响排序的问题、原文片段、原因、改法与边界；不编辑文件。
- `annotated`: 改写稿 + 简短关键变更说明 + 仍待作者确认的问题。
- `diff`: 原文与改写对照，便于审阅；不要声称机器计算的精确 diff（除非实际运行了 diff 工具）。
- `diagnosis`: 专门用于定位问题，包含判断依据和待验证事项；不默认给出整篇新稿。

## 8. 保真与文件保护协议

### 8.1 永不擅改的内容

除非用户明确授权且能验证准确：

- 数字、百分比、币种、单位、日期、时间、版本号
- 人名、组织名、产品名、地名和专业术语
- “可能”“通常”“仅”“至少”“不超过”“计划”“据报道”等限定
- 否定、例外、适用范围、比较基准、归因和引文内容
- 代码块、行内代码、SQL、JSON、YAML、shell 命令、正则表达式、公式
- URL、Markdown 链接目标、图片路径、锚点、文件路径、接口路径、环境变量
- 表格中的数据和列含义
- 用户指定的原文段落、法律条款、合规声明、学术引文

### 8.2 Markdown 文件编辑规则

- 仅修改用户授权的自然语言正文；代码块与 frontmatter 默认只读。
- 默认不改标题文字、层级与顺序，避免自动锚点、目录和站内链接失效。
- `deep` 模式授权标题/结构变更时，应同步检查目录、锚点、内部链接、脚注引用与列表编号。
- 保留每项独立事实；列表即使很长也不能为了精简而删除条目。
- 对不一致的数据**报警而非猜一个正确值**。
- 保留示例所表示的实际机制；不为了口语化破坏操作精度。

### 8.3 特殊高风险文本

- 医疗：区分症状、诊断、可能性和建议；不增加治疗方案。
- 金融：不新增收益预测、风险水平或投资建议。
- 法律：不改责任主体、例外、义务程度、期限和条件。
- 科研：不强化结论，不增加统计显著性或因果性，不删局限性。
- 安全操作：保留必要重复提醒，不能删除可能影响安全的步骤。

## 9. 教学示例：展示“好懂”的判据

以下输入均为**独立构造示例**，无隐含外部资料，展示的不是运行测试结果。

### 示例一：长定语

**原文**

> 对于在提交申请后未在规定期限内完成身份核验且未主动撤回申请的用户，系统将自动终止申请流程。

**优化**

> 用户提交申请后，如果没有在规定期限内完成身份核验，也没有主动撤回申请，系统会自动终止申请流程。

**改动原因**：把执行对象前移，按提交 → 条件 → 结果的顺序阅读；保留两个条件和原来的触发关系。

### 示例二：名词堆叠

**原文**

> 该平台提供跨部门任务状态协同跟踪能力。

**优化**

> 这个平台可以让不同部门一起跟踪任务状态。

**改动原因**：还原行为角色和动作，没有新增功能。

### 示例三：句子已经清楚，不改

**原文**

> 先保存文件，再关闭窗口。未保存的修改会丢失。

**优化**

> 先保存文件，再关闭窗口。未保存的修改会丢失。

**原因**：原句没有明显理解障碍，改写不必留下痕迹。

### 示例四：歧义不可擅自消除

**原文**

> 张老师把资料交给李老师后，他发现有两页缺失。

**正确处理**

> `review`：`“他”可能指张老师或李老师。请确认是谁发现缺页，确认前不改写。`

**错误做法**：直接改成“李老师发现有两页缺失”。

### 示例五：保留不确定性

**原文**

> 该问题可能与缓存有关，但目前没有证据确定原因。

**优化**

> 这个问题可能与缓存有关，但原因还没有确定。

**原因**：保留“可能”和“原因未确定”。

### 示例六：结论与依据的阅读顺序

**原文**

> A 地区去年开店 120 家，B 地区开店 80 家。A 地区开店数量更多。

**面向决策者的结构改写（获得授权时）**

> 去年，A 地区开店数量比 B 地区多：A 地区为 120 家，B 地区为 80 家。

**原因**：先给结论，再给依据；没有把开店数解释为销售额或盈利能力。

### 示例七：保留专业精度

**原文**

> 接口返回 HTTP 429 时，客户端应根据 Retry-After 响应头决定重试时间。

**优化**

> 接口返回 HTTP 429 时，客户端应根据 Retry-After 响应头决定重试时间。

**原因**：对专业读者已经明确，不把协议名改成模糊概念。

### 示例八：禁止凭空补充的“通俗解释”

**原文**

> 系统基于多源数据评估候选位置。

**可接受优化**

> 系统会结合多个来源的数据，评估一个备选位置。

**禁止优化**

> 系统结合客流、人口、租金、竞品销量和消费画像，为店铺预测未来一年营收。

**原因**：原文没有列数据来源，更没有提收入预测。即使这样写更具体，也属于编造。

## 10. 评估体系：让“更易理解”成为可检验的目标

### 10.1 不使用的伪指标

- `AI 检测器判定为真人写作的比例` —— 与可理解性不等价。
- `改写后字数下降比例` —— 删除必要信息可能适得其反。
- `平均句长越短越好` —— 短句也可能断裂、含糊。
- `模型自评 9.8/10` —— 不能单独证明读者理解改善。
- `独立于上下文的术语数量` —— 必要术语删除可能损害精度。

### 10.2 核心衡量指标

| 指标 | 定义 | 优先级 | 说明 |
|---|---|---|---|
| **理解题正确率** | 读者读完后回答文章事实、条件、例外、因果边界的正确率 | P0 | 主要结果指标 |
| **事实保真率** | 原文独立命题保留比例 + 新增无依据命题数 | P0 | 上线阻断项 |
| **完成时间** | 阅读与答题耗时 | P1 | 在理解正确率不下降的前提下比较 |
| **主观理解难度** | 读者报告理解费力度 | P1 | 与客观测量相互印证 |
| **回读次数** | 为解决歧义重复阅读片段的次数 | P2 | 可由阅读实验记录，非必要 |
| **术语解释准确率** | 专业术语及其边界有无被误解 | P1 | 专业场景重要 |
| **无谓改写率** | 原本清楚的内容被改坏或无意义替换的比例 | P1 | 防止过度编辑 |
| **模型间稳定性** | 不同 Agent/模型对核心约束的遵循情况 | P2 | 衡量规则可迁移性 |

**建议主要判定逻辑：** 只有在事实保真没有明显下降、且理解正确率有可重复改善时，才宣称可理解性提升。若只有主观偏好提升，应明确说“读起来更舒服”，不要改称“理解准确率提高”。

### 10.3 测试集设计

初版至少包含六组文本：

1. **句法困难：** 长定语、复杂嵌套、跨度远的主谓搭配。
2. **语义歧义：** 人物指代、否定范围、条件关联、复杂比较。
3. **术语门槛：** SaaS 产品说明、技术参数、数据报告、科普内容。
4. **篇章结构：** 背景-结论顺序错误、段间缺桥梁、前后术语不一致。
5. **高风险保真：** 医疗、金融、法律、科研结论中的限定与否定。
6. **负样本（必须不改）：** 已经清楚的操作说明、精确术语、合同条件、代码和公式。

**建议首发门槛**：至少 30 条人工检查的公开合成案例，每组不少于 5 条；每条提供原文、目标读者、问题类型、保留点、允许改法和禁止改法。此门槛是**项目的目标要求**，不是已完成数据。

### 10.4 A/B 实验方法

用相同来源文本建立三个版本：

- `A` 原文
- `B` 经过 Humanizer-zh 或普通语言润色（作为一个比较基线）
- `C` 经过 Comprehensibility-zh

每位参与者**对同一篇文章只读一个版本**，避免记忆污染；不同文章在参与者之间做随机平衡。将读者按经验层级分组，盲化展示来源，不告知哪个版本由哪个 Skill 改写。所有版本先经过人工事实保真复核。

每篇设计 3–5 道问题：关键信息、条件/例外、因果边界、行动理解。记录正确率、耗时、阅读难度，预先说明成功条件。不要只选“优化后更好看”的例子；失败案例也应公开。

建议第一轮用 **20–30 篇文本、每种版本累计足够的独立读者回答** 作为探索性试验，再根据方差与目标最小效果量做正式样本量估算。这里不给出未经计算的统计显著性承诺。

### 10.5 自动化测试与人工评审分层

- **静态检查（可 CI）：** frontmatter 可解析、文件结构存在、内部引用有效、测试样本字段齐全。
- **语义约束检查（需人工/模型辅助）：** 数字、主体、条件、否定、推断程度没有漂移；发现风险须人工确认。
- **可理解性评估（需真人）：** 理解题、读速与回读情况；不能由上述静态检查替代。

## 11. 仓库设计

### 11.1 推荐目录

```text
comprehensibility-zh/
├── README.md                      # 对公众介绍、安装与使用
├── SKILL.md                       # Agent 直接执行的核心指令
├── LICENSE                        # MIT，使用正式 LICENSE 文本
├── CONTRIBUTING.md                # 社区贡献规则
├── CHANGELOG.md                   # 版本与兼容性变化
├── docs/
│   ├── DESIGN.md                  # 核心设计和规则系统
│   ├── EVALUATION.md              # 评估方案与证据边界
│   └── RESEARCH.md                # 科研参考、局限性和致谢
├── examples/
│   └── examples.md                # 公开示例（均为合成示例）
├── tests/
│   ├── fixtures.json              # 合成测试数据，不含私人原文
│   └── test_repository.py         # 元数据和测试夹具静态校验
└── .github/
    └── workflows/
        └── validate.yml           # 无模型依赖的自动化结构测试
```

首发采用**根目录 `SKILL.md`**：对单一 Skill 仓库最直观。未来有多个 Skill 时再引入 `skills/comprehensibility-zh/SKILL.md`，迁移前测试安装发现行为。

### 11.2 软件架构原则

**v0.1 是规则驱动的 Agent Skill，不是独立的机器学习模型，也不是有精确可重复评分的算法软件。**

建议两层组织：

- **执行核心层（SKILL.md）：** 最短可用流程、优先级、禁止事项、主要错误类型、模式和输出规则；Agent 每次使用必读。
- **参考知识层（docs/）：** 详细分类、案例、评估方法、研究边界；需要时才加载，避免挤占 Agent 上下文。

**不推荐 v0.1 就做“可理解性评分 0–100”**。未经中文读者数据校准的分数会制造虚假的科学感。可以输出高/中/低风险的诊断排序，但只能标注为编辑判断。

### 11.3 模式与实际能力表

| 能力 | v0.1 | v0.2 计划 | v1.0 愿景 |
|---|---|---|---|
| 文本审阅、局部改写、深度重构 | ✅ 基于提示指令 | 改善规则 | 继续增强 |
| Markdown 文件保护 | ✅ 指令级 | 增加 AST 工具 | 更可靠验证 |
| 跨 Agent 安装 | ✅ 依赖兼容客户端 | 加入兼容性矩阵 | 主流客户端验证 |
| 事实保真 | ✅ 编辑自检 + 人工核对 | 半自动比对 | 公开量化评价 |
| 真人理解实验 | ❌ 首发未完成 | 小规模研究 | 常态化基准 |
| CLI 与 API | ❌ 不宣称支持 | 可选实验接口 | 根据需求决定 |
| 精确可理解性评分 | ❌ | 不宜贸然加入 | 必须先验证 |

这里 ✅ 表示**设计在随附 Skill 中提供的可执行指令**，不是实测覆盖率或效果保证。

## 12. 规则执行中的关键难题

### 12.1 当文案既抽象又没有细节

不能凭空补充场景、对象或数据。优先改写为语言上清楚、但保留原有概括程度的表达。若问题来自**内容欠缺**而非**表达方式**，在 `review` 模式明确标注为“资料不足”，不要伪装修辞可解决。

### 12.2 如果想让客户觉得“特别容易理解”

仅在用户授权内容重组时，按读者关心的问题组织章节。例如：

`这个产品解决什么问题 → 它怎么做 → 我能看到什么结果 → 有哪些适用条件和限制 → 我下一步该怎么操作`。

需要证据但文档没有时标注资料缺口。不得擅加使用案例、性能数字或竞品优劣。

### 12.3 “短句就是好句”吗

不是。机械拆句可能丢掉转折、因果、条件等逻辑关系。判断标准是**读者能否读对各句之间的关系**，而不是句号数量。

### 12.4 “低频词”一定难懂吗

不是。专业术语在专家领域可能非常常见且非常精确；名字、机构、符号不能因为生僻而删除。规则必须结合领域、读者和上下文。

### 12.5 是否用大模型作为裁判

可用来找候选问题和检验数字、条件等明显漂移，但不能让模型给自己的改写打高分，就当成真人理解结果。最好将生成者与评审者分开，且人工复核重要改动。

## 13. 社区贡献与开放治理

### 13.1 许可证建议

项目原创文本、示例和测试代码使用 **MIT** 许可证，提供仓库根目录完整 `LICENSE` 文件。第三方材料只采用链接和独立概述，不直接搬运论文图表或其他 Skill 的大量规则原文。若后续引入他人代码、文本或数据，按原始许可作显著署名与告知。

### 13.2 欢迎贡献的内容

- 典型但未包含敏感个人信息的中文难读案例。
- 有明确“原文、问题、修改原因、保留点、反例”的规则建议。
- 不同读者群体的专业文本与研究证据。
- 对真人理解测试设计、盲测和统计的改进。
- Agent/IDE 兼容性测试与文档安全问题。

**不接受**：AI 检测规避营销、编造数据的“改写”，未经授权上传客户材料或私人对话、以假想分数证明效果的 PR。

### 13.3 PR 模板（建议）

```text
问题：
目标读者：
原句（已确认可公开）：
为什么会妨碍理解：
推荐改法：
必须保留的事实/限定：
不该改写的反例：
测试方式：
是否含第三方受版权保护或敏感内容：
```

### 13.4 版本管理

- `0.1.x`：措辞微调与示例/说明修复；不应改变基本保真承诺。
- `0.2`：增加标准化测试、对复杂 Markdown 的验证与跨 Agent 兼容文档。
- `1.0`：具备公开、可复现的中文评价集、稳定规则和明确适用边界，最好包括真人理解实验。

## 16. 常见问题（FAQ）

**Q：这是 Humanizer-zh 的 Fork 吗？**  
不是。它是一个目标不同、规则独立编写的互补 Skill，前者更关注自然表达，后者更关注读者理解成本。

**Q：它能让 AI 文章“更像人写的”吗？**  
有时可能让文字更自然，但这不是设计目标，也不保证任何检测器结果。

**Q：改写后字数会增加吗？**  
可能。必要的解释、连接词与分句可以降低读者负担，长度没有固定优化方向。

**Q：能自动补充例子吗？**  
只能展开原文已有事实。若用户明确授权生成“虚构教学示例”，必须清楚标记为虚构，不能当作原文事实或真实案例。

**Q：能直接对 PDF、网站、GitHub 仓库执行吗？**  
核心是文本编辑指令。读取 PDF、网页和仓库的能力取决于宿主 Agent 的工具；不应宣称 Skill 自带这些抓取能力。文件编辑同样取决于用户授权与工具权限。

**Q：是否支持 Claude Code、Codex、Cursor？**  
按开放 Agent Skills 格式设计；具体加载路径、可用工具与版本可能不同，应以各客户端当前文档和实测为准。

**Q：为什么不用一个“中文可读性分数”？**  
未经中文实证校准的综合数字容易误导。首发以可解释的问题诊断和真实读者测试为主。

**Q：对中文研究论文是否适用？**  
适合改进句法和结构，但须保留专业定义、理论限定、引用与统计表达；不能为了通俗而改变科学意义。
